# Multi-Tenancy at 7,000 Tenants in One Environment

*Research note for graph-memory-platform · 2026-10-20. Sources: ClickHouse official docs/KB, Altinity KB, Neo4j/Memgraph/AuraDB docs, AWS Builders' Library.*

## TL;DR

- ClickHouse's own multi-tenancy guide recommends the **shared table + `tenant_id` in the primary key + row policies** model "as this is the simplest to manage" and states it is "particularly effective for handling a large number of tenants (potentially millions)"; for separate tables and separate databases it warns, verbatim: "Note this approach doesn't scale for 1000s of tenants" ([ClickHouse multitenancy guide](https://clickhouse.com/docs/cloud/bestpractices/multi-tenancy)).
- Hard guardrails dispose of database-per-tenant at 7k: recommended max of **"1000 databases and 5000 tables, 50000 partitions, and 100000 parts"** per service (KB, Sep 1, 2021) ([docs](https://clickhouse.com/docs/knowledgebase/maximum_number_of_tables_and_databases)); Cloud defaults: Databases 1000, Tables 5000, Views 15000, Named collections 1000 (private preview), Parts 10k, Query concurrency 1000/replica; single-replica services: 100 DBs / 500 tables ([usage limits](https://clickhouse.com/docs/cloud/bestpractices/usage-limits)).
- 7,000 tenants × even 3 tables ≈ 21,000+ tables (~4× the 5,000 guardrail) with startup-time cost; Altinity: "ReplicatedXXXMergeTree = few hundreds is still acceptable" system-wide, non-replicated "few thousands", and > several tens of thousands of parts leads to "slow starts" ([Altinity KB](https://kb.altinity.com/altinity-kb-schema-design/how-much-is-too-much)).
- Isolation without namespaces: ClickHouse quotas support **keyed quotas** — "the quota_key 'key' is passed in the query parameter, and the quota is tracked separately for each key value" — i.e., per-tenant accounting with a **single shared DB user**; plus `queries_per_normalized_hash`, settings profiles, and `max_concurrent_queries_for_user` ([quotas](https://clickhouse.com/docs/en/operations/quotas), [session settings](https://clickhouse.com/docs/reference/settings/session-settings/max-concurrent)).
- Row policies are the storage-side tenant wall, but they are **readonly-only** ("Row policies make sense only for users with readonly access") and get dropped on `Distributed` reads unless defined on local tables (errors with `ILLEGAL_PREWHERE`); `serialize_query_plan = 1` bypasses per-server policies ([row policy docs](https://clickhouse.com/docs/en/sql-reference/statements/create/row-policy)).
- Graph-layer analog: **no major graph vendor serves 7,000 isolated graph instances in one cluster.** AuraDB multi-database GA (Oct 8, 2026) caps at **max 100 (Business Critical) / 250 (VDC), up to 5 databases per GB of RAM**; AuraDB Professional is hard-limited to **1 database per instance** ([docs](https://neo4j.com/docs/aura/managing-instances/multiple-databases), [quotas](https://neo4j.com/docs/aura/quotas-and-limits/)). Memgraph's multi-tenancy (Enterprise, May 2024) namespaces "share the same underlying memory and processing resources" with no per-database config ([Memgraph docs](https://memgraph.com/docs/database-management/multi-tenancy)); Neo4j composite/Fabric is addressing indirection, "does not store data independently" — not isolation.
- Therefore "schema-per-tenant" at 7k is isolation theater: it buys no isolation threshold worth the price — the actual cost is **registry and replay overhead in ClickGraph** (7,000 YAML schemas parsed per node; worst-case boot replay ≈ 7,000 × `SCHEMA_REPLAY_MAX_ROWS` rows + 7,000 × `MAX_BYTES`) and it forces per-tenant physical tables upstream.
- Recommended: **shared ledger + shared physical graph keyed by `tenant_id`, tenant scoping injected in ClickGraph's Cypher→SQL translation ("row policy at the graph layer"), per-tenant quotas via keyed `quota_key`/registry rows, per-tenant token buckets + fair batch workers at the API.**
- Blast radius: quotas + async inserts + 1M-row batch blocks make one tenant's backfill that tenant's problem; separate infrastructure is justified only per **tenant class** (e.g., a whale/regulated tier), not per tenant.

## 1. ClickHouse tenancy patterns at thousands of tenants

ClickHouse Cloud's guide lays out four live options with explicit fit boundaries ([multitenancy guide](https://clickhouse.com/docs/cloud/bestpractices/multi-tenancy)):

1. **Shared table** — all tenants in one table, `tenant_id` in the ORDER BY/key, access via row policies. Recommended positioning: "We recommend this approach as this is the simplest to manage, particularly when all tenants share the same data schema and data volumes are moderate (< TBs)… This method is particularly effective for handling a large number of tenants (potentially millions)." Caveat: big/small tenant skew "is largely mitigated by including the tenant field in the primary key."
2. **Separate tables** — "good choice when tenants have different data schemas… a few tenants with very large datasets where query performance is critical"; explicit: "Note this approach doesn't scale for 1000s of tenants."
3. **Separate databases** — useful "if each tenant requires a large number of tables and possibly materialized views, and has different data schema. However, it may become challenging to manage if the number of tenants is large," plus the same doesn't-scale warning.
4. **Separate cloud service** — "less common… a solution if tenants data are required to be stored in different regions - for legal, security or proximity reasons."

The quantitative wall: the KB says "a maximum of 1000 databases and 5000 tables, 50000 partitions, and 100000 parts across all databases for a service. Databases in ClickHouse are more of a *namespace* and have no performance impact; 1000 databases is a loose guideline. However, the number of tables would affect the service startup time" ([KB, Sep 1, 2021](https://clickhouse.com/docs/knowledgebase/maximum_number_of_tables_and_databases)). Cloud turns that into enforced guardrails ([usage limits](https://clickhouse.com/docs/cloud/bestpractices/usage-limits)): Tables 5000, Views 15000, Dictionaries 5000, **Named collections 1000 (private preview)**, Partitions 50k, Parts 10k (`max_parts_in_total`), Part size 150 GB, Query concurrency 1000/replica, and "For Single Replica Services, the maximum number of databases is restricted to 100, and the maximum number of tables is restricted to 500."

Altinity's operator KB (self-managed) agrees: replicated MergeTree tables "few hundreds is still acceptable" system-wide (each adds replication-queue housekeeping), non-replicated "few thousands", databases "Dozens / hundreds is usually still acceptable", and >several-tens-of-thousands of parts leads to "slow starts" — degradation cliffs, not hard errors ([Altinity KB "How much is too much"](https://kb.altinity.com/altinity-kb-schema-design/how-much-is-too-much)). Real projects ship the shared-table pattern: jaeger-clickhouse has a documented multi-tenant mode with a `tenant` column in shared tables ([guide](https://github.com/jaegertracing/jaeger-clickhouse/blob/main/guide-multitenancy.md)).

**Partition discipline matters more than engine choice:** tenant_id must not be a partition key (7,000 tenants × time periods explodes `system.parts` toward the 50k/100k limits) — partition by time only, tenant in the sort key (`ORDER BY (tenant_id, ts)` exactly as the docs example does).

## 2. Isolation mechanics inside one service

- **Quotas** ([docs](https://clickhouse.com/docs/en/operations/quotas)): interval-scoped counters — `queries`, `errors`, `result_rows`, `read_rows`, `written_rows/bytes`, `execution_time`, and `queries_per_normalized_hash` ("up to 100 instances of each distinct normalized query per hour") for flood-of-repeated-patterns control. Critically, quotas are **keyed**: "`<keyed />` — The quota_key 'key' is passed in the query parameter, and the quota is tracked separately for each key value. For example, you can pass a username as the key, so the quota will be counted separately for each username." One shared ClickHouse user + `quota_key = tenant_id` = per-tenant accounting without 7,000 DB identities. Note the caveats: distributed accounting sits on the requestor server, and "When the server is restarted, quotas are reset" (stateless — pair with your own durable metering).
- **Settings profiles / concurrency / memory** ([max_concurrent session settings](https://clickhouse.com/docs/reference/settings/session-settings/max-concurrent), [concurrency KB](https://clickhouse.com/docs/resources/support-center/knowledge-base/general-faqs/concurrency)): `max_concurrent_queries_for_user` ("The maximum number of simultaneously processed queries per user") is a profile setting; Cloud runs `max_concurrent_queries_for_all_users = 1000` per replica by default. Per-tenant classes map to profiles clamping `max_memory_usage`/`max_threads`/`max_concurrent_queries_for_user` — usable even with the shared user by setting per-query settings alongside `quota_key`.
- **Row policy** ([docs](https://clickhouse.com/docs/en/sql-reference/statements/create/row-policy)): the "extra WHERE on every query" wall — `CREATE ROW POLICY … USING tenant_id = 42 TO role`, restrictive policies AND-combined. Three traps for a graph layer connecting with **one service account**: (1) policies bind to users/roles, so they don't help a single service user — the filter must be generated by the application (`additional_table_filters` pattern, [Oneuptime walkthrough](https://oneuptime.com/blog/post/2026-03-31-clickhouse-multi-tenant-api-layer/view)); (2) policies on `Distributed` wrappers error with `ILLEGAL_PREWHERE` — define them on local tables; (3) `serialize_query_plan = 1` ships prebuilt plans that bypass remote row policies (issue #112891) — keep it off for scoping-critical users.
- **Backup granularity**: `BACKUP TABLE`/`BACKUP DATABASE` are first-class targets ([backup docs](https://clickhouse.com/docs/en/operations/backup)). DB-per-tenant gets free per-tenant restore points; the shared-table model gets per-tenant restore only via tenant-filtered export/replay — a real, but serviceable, regression.
- **Cloud "isolation" primitives are per service, not per tenant**: separate pods, Keepers, storage subpaths; Warehouses = "a set of services that share the same data" ([warehouses docs](https://clickhouse.com/docs/cloud/reference/warehouses)); billing metered **per service in compute units (1 unit = 8 GiB + 2 vCPU)** with per-service usage display — **no per-tenant billing or premetering** ([architecture](https://clickhouse.com/docs/en/cloud/reference/architecture), [pricing overview](https://clickhouse.com/docs/cloud/manage/billing/overview)). Isolation economics come from ClickHouse itself (quotas/profiles/row policies).

## 3. The graph-layer analog: N schemas vs one shared graph (the key question)

**What vendors actually do.** Neo4j built multiple databases per DBMS for precisely the multi-tenant case, then put a ceiling on it: AuraDB multi-database GA (Oct 8, 2026) allows **"Up to 5 databases per GB of RAM, to a maximum of 250 on Virtual Dedicated Cloud and 100 on Business Critical"**, "All databases share the instance's compute and memory resources", billing unchanged regardless of database count, and Professional tier = **1 database per instance** ([docs](https://neo4j.com/docs/aura/managing-instances/multiple-databases), [quotas](https://neo4j.com/docs/aura/quotas-and-limits/)). Neo4j 4.x Fabric / 5.x composite databases give a `USE`/alias addressing layer, but composite databases "do not store data independently" ([operations manual](https://neo4j.com/docs/operations-manual/current/database-administration/composite-databases/concepts/)) — query routing, not a resource wall. Memgraph multi-tenancy (Enterprise, May 2024) namespaces "share the same underlying memory and processing resources", and "there is no way to specify a per-database configuration" ([multi-tenancy](https://memgraph.com/docs/database-management/multi-tenancy), [system config](https://memgraph.com/docs/database-management/system-configuration)). **Read the curve, not the marketing**: vendors cap isolated graphs per cluster in the hundreds and bill per instance beyond — nobody ships 7,000 co-resident isolated graphs, because per-instance metadata, memory partitioning, and per-namespace ops all go superlinear.

**Applied to ClickGraph** (named YAML graph schemas, HTTP `/schemas/load`, persistence registry, `CLICKGRAPH_SCHEMA_PERSISTENCE`, `CLICKGRAPH_SCHEMA_REPLAY_MAX_ROWS/MAX_BYTES`):

- **Schema-per-tenant (7,000)**: 7,000 registry rows are trivial for ClickHouse — the real costs live elsewhere: 7,000 YAML graphs parsed into memory in every ClickGraph replica at boot; worst-case boot replay **7,000 × REPLAY_MAX_ROWS rows and 7,000 × MAX_BYTES** swept before the first query serves (an example 10k-row cap → up to 7×10⁷ rows); per-tenant schema names imply per-tenant physical tables upstream, dragging storage into the "doesn't scale for 1000s of tenants" class; and 7,000-way schema drift = 7,000 DDL/migration line items plus a second control plane for `/schemas/load`.
- **One shared graph + tenant scoping**: one schema, one registry row; every node/edge row carries `tenant_id`; ClickGraph's Cypher→SQL compiler injects the tenant predicate as a per-request-bound query parameter (never request-embedded ids — the injection hazard the [Oneuptime post](https://oneuptime.com/blog/post/2026-03-31-clickhouse-multi-tenant-api-layer/view) also flags). This IS the missing piece ClickHouse can't give here (row policies need per-tenant users; we have one service user) — a "virtual row policy at the graph layer": compiler-enforced, centrally tested (one filter, not 7,000 configs), free per tenant. Direct precedent: AshClickhouse's "attribute" strategy injects "a `tenant_id = ?` filter into every query" at the data layer, noting "ClickHouse has no row-level security" it can rely on ([docs](https://ash-clickhouse.hexdocs.pm/0.7.0/multitenancy.md)). The knobs become quota/profile levers, not schema copies.

**Verdict:** vendor behavior + ClickHouse guidance both point one way — the shared graph with tenant scoping is the only architecture that holds at 7k without either exploding ClickHouse metadata or exploding ClickGraph's registry/replay budgets.

## 4. Per-tenant keys/quotas at the API layer

AWS's canonical fairness writeup (David Yanacek, Builders' Library, Sep 2020) prescribes: shape traffic with **rate limiting**, enforce **quotas per tenant/workload**, and implement admission control with **token buckets** — "Tokens are added to the bucket at a configured rate, up to a maximum capacity… known as the burst capacity," and to keep burst safe, **compose buckets** ("one token bucket can have a relatively low rate and a high burst capacity, and a second bucket … a high rate and a low burst capacity") ([Fairness in multi-tenant systems](https://aws.amazon.com/builders-library/fairness-in-multi-tenant-systems)). Applied here: one bucket per tenant, never a global one — "Per-tenant buckets turn a flood into that tenant's own problem" — composed burst admission on the write path, per-request throttle-key logging for fleet-wide fairness auditing, and **fair batch queues** that "interleave per tenant so one backlog doesn't become everyone's latency" (SQS fair queues) ([SAS02 pattern writeup](https://builder.aws.com/content/3HB21wIwHVIVH3c9BkcRGVC3sXR/sas02-fairness-admit-on-a-forecast-reconcile-on-actuals)). The rationale (AWS): "if the overall load increases abruptly on a service, that increase is most likely driven by a single tenant. With fairness in mind, we want to avoid failing some number of requests across all tenants" — admit-then-isolate, don't shed globally.

## 5. Control plane and blast radius

- **Onboarding** in the recommended model = allocate tenant_id + one quota/config row (+ signal topic), **zero DDL**: versus DB-per-tenant (CREATE DATABASE + k tables + grants) or graph-schema-per-tenant (HTTP `/schemas/load` + persist + replay budget). 
- **Offboarding** = revoke scoping/rule first (instant, reversible), then async partition/data drop by `(tenant_id, time)` — soft delete before hard delete keeps audit replay possible. 
- **Audit/metering**: quotas "output to the server log after each request" per interval ([quotas](https://clickhouse.com/docs/en/operations/quotas)); `system.user_processes` gives per-user memory/peak and ProfileEvents ([docs](https://clickhouse.com/docs/reference/system-tables/user_processes)) — project onto `quota_key` for per-tenant cost lines.
- **Blast radius of a big backfill**: bounded by the tenant's token bucket + quota (`written_rows/bytes`, `query_inserts`), async-insert buffering ("a new part only after the buffer size exceeds a configurable threshold, or a timeout expires", [parts docs](https://clickhouse.com/docs/managing-data/core-concepts/parts)), and "Anything > 1M rows is split into 1M-row blocks" ([usage limits](https://clickhouse.com/docs/cloud/bestpractices/usage-limits)).

## Decision table

| Architecture | Isolation at 7k | Cost / feasibility at 7k | Ops burden | Graph-layer fit | Verdict |
|---|---|---|---|---|---|
| A. Shared tables/ledger + `tenant_id` (row policies + keyed quotas) | Logical wall when tenant predicate is compiler-enforced; row policies if/when per-tenant users exist | Cheap: 1 schema, N quota rows; no metadata cliff (well under 5000 tables / 1000 DBs) | Low: one schema, one migration; onboarding = row insert | **Best**: one shared graph, scoping injected at Cypher→SQL; replay = one budget | **RECOMMEND** for mainline 7k |
| B. Database-per-tenant | Strong (true namespace) | Impossible: 7,000 DBs ≫ 1000-DB/5000-table guardrails; 4-11× the metadata budget; slow starts | Very high: 7k × DDL/grants/backup jobs | Poor: ClickGraph = 7k YAML schemas, 7k× replay rows, 7k migrations | Reject |
| C. Tier/warehouse split (per-tenant-class compute) | Real compute walls per class (whale vs long-tail) | Moderate: only a handful of clusters (well under the 20-service soft org cap) | Medium: 2-4 configs, tenant-class routing | Good: same shared graph model, run per tier | Keep as an escape hatch for whales/regulated |
| D. Separate service per tenant | Max | At 7k: ruinous per-service compute units + org soft caps ("Services per organization, 20 (soft)") | Worst | Requires per-tenant infra registry | Reject for long tail |

**Recommendation for the spec:** **A shared ledger + `tenant_id` + shared graph with tenant scoping + per-tenant quotas** (keyed `quota_key`/profiles/token buckets), with **C as a bolted-on tier** (≤ 5 whale/regulated clusters). Evidence: ClickHouse explicitly recommends the shared-table model up to "potentially millions" of tenants and disqualifies namespace-per-tenant at 1000s; graph vendors' own multi-database products cap at ≤250 instances; and ClickGraph's own budget knobs (`REPLAY_MAX_ROWS/MAX_BYTES` × 7,000 schemas) make the schema-explosion cost measurable and large. Name the hybrid escape hatch up front so a whale tenant has a graceful path out of the shared pool.

## So what for the spec

1. **One schema, one graph, tenant-scoped**: `tenant_id` on every node/edge row + compiler-injected tenant filter in ClickGraph — scoping is structural, never a hand-pasted `WHERE`.
2. **Quota key = tenant_id on a single shared service user**; add `queries_per_normalized_hash` for repeated-pattern flood control and a durable metering table (quota state is lost on restart).
3. **Keep DELETE/INSERT per tenant bounded**: use same token bucket at ClickGraph admission per tenant; separate limits for interactive vs batch traffic.
4. **Don't partition by tenant**: `(tenant_id, time)` in ORDER BY only, time partitions only — protects the shared 50k-partition / 10k-part envelope.
5. **Onboarding is metadata-light**: tenant row + quota row + signal topic; no DDL; no `/schemas/load` fan-polling (schema persistence stays flat, one graph).
6. **Offboarding two-phase**: revoke → async drop, with audit retention before data deletion.
7. **Hybrid tier by tenant class** (not tenant): at most a few CPU/memory clusters for whales; routing via a tenant-class map; the 20-services-per-org soft cap is the ceiling to plan against.
8. **Per-tenant restore** = tenant-filtered export/replay; ship it operationally early, since shared tables lose free BACKUP-per-tenant granularity.
9. **Meter everything per tenant** from day 1 (`system.user_processes` + quota logs + request logs with the throttle key) — needed for cost allocation and noisy-neighbor forensics.
10. **Writes**: keep inserts async and batch-bounded (1M-row blocks, async-insert buffering); size the 7k-tenant concurrency envelope around the 1000-concurrent/replica ceiling and watch `max_concurrent_queries_for_user` under a single shared user.
