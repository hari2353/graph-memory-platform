# 02 — Ingestion: CloudEvents, multi-broker delivery, and ClickHouse ledger writes

_2026-10-20 · primary sources: CloudEvents spec, Apache Kafka, Apache Pulsar, NATS, AWS, Microsoft, RabbitMQ, ClickHouse docs/blog._

## TL;DR

- **Adopt CloudEvents 1.0.2**: required `id`+`source` (uniqueness contract), `specversion`, `type`; optional `dataschema`, `subject`, `time` map 1:1 onto ledger columns ([spec](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md)).
- The spec's **`partitionkey` extension** ("causal relationship/grouping", example: "the ID of the entity the event is associated with") is the official per-user ordering knob ([partitioning extension](https://github.com/cloudevents/spec/blob/main/cloudevents/extensions/partitioning.md)).
- Every broker here is **at-least-once** end-to-end; Kafka's "exactly-once" does not escape the broker ([Kafka design](https://kafka.apache.org/42/design/design/)) — the ClickHouse write path must be idempotent, not "exactly once."
- Ledger-grade brokers: Kafka + Pulsar (retained log, native ordering, best adapters); NATS JetStream acceptable (2-min dedup caveat); SQS/Service Bus/RabbitMQ are buffers only — no replay.
- ClickHouse dedups **identical retried inserts** via block ids (`insert_deduplication_token` for caller-chosen ids) — but plain `MergeTree` non-replicated has dedup **off by default** ([dedup-on-retries](https://clickhouse.com/docs/concepts/features/operations/insert/deduplicating-inserts-on-retries)).
- Batch law: ≥1,000 rows, ideally 10k–100k, ~1 insert/s per table ([insert strategy](https://clickhouse.com/docs/concepts/best-practices/selecting-an-insert-strategy)); async inserts shift batching server-side with gotchas (whole-query rejection, no DLQ in fire-and-forget) ([async inserts](https://clickhouse.com/docs/optimize/asynchronous-inserts)).
- Capacity anchors: **~100k rows/s obtainable per Kafka table engine** ([Kafka engine](https://clickhouse.com/docs/integrations/kafka/kafka-table-engine)); operators sustain 11M rows/s (Cloudflare) ([async-inserts blog](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse)).
- Broker retention is finite/inconsistent (NATS dedup 2 min; Kinesis ≤365 days) — **the ClickHouse ledger, not the broker, is the replayable truth**; the projector must be replay-safe.

## 1. CloudEvents 1.0.2 as the signal envelope

Four REQUIRED attributes: `id` (non-empty, unique per producer), `source` (URI; **`source`+`id` uniquely identifies an event** — re-sends MAY reuse the id, and consumers MAY treat identical `source`+`id` as duplicates), `specversion` (`"1.0"`), `type` (SHOULD be reverse-DNS, e.g. `com.github.pull_request.opened`). OPTIONAL: `datacontenttype`, `dataschema` (URI of the `data` schema; incompatible changes SHOULD use a new URI), `subject`, `time` (RFC 3339). All implementations MUST support the JSON event format; intermediaries MUST forward events ≤64 KB, consumers SHOULD accept 64 KB; sensitive data SHOULD NOT sit in context attributes ([spec](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md)). The spec defines no partitioning/ordering/delivery semantics — those belong to brokers; the **`partitionkey`** extension ("a partition key for the event… typically for defining a causal relationship/grouping") fills that gap and maps to every broker's ordering primitive ([partitioning extension](https://github.com/cloudevents/spec/blob/main/cloudevents/extensions/partitioning.md)).

**Envelope proposal:** CloudEvents 1.0.2 JSON; `type`=`com.graphmemory.signal.<name>.v<n>`; `partitionkey=user_id` REQUIRED; `dataschema` → per-type schema-registry URI; `subject`=entity id. No custom envelope needed.

## 2. Broker comparison for this use case

Scope: app emission → ClickHouse ledger, plus replay for projector rebuilds.

| Broker | Delivery semantics | Per-user ordering | Replay | Adapter effort |
| --- | --- | --- | --- | --- |
| **Kafka** | Non-idempotent retry = at-least-once; idempotent producer dedups by producer-id+sequence; exactly-once only when producing back into Kafka, not to external stores ([design §Delivery Semantics](https://kafka.apache.org/42/design/design/)) | "Totally ordered partitions, each… consumed by exactly one consumer… in each subscribing consumer group"; user-id key → same partition ([design](https://kafka.apache.org/42/design/design/)) | Log replay via offset reset; retention within configured/Tiered-storage limits | **Lowest** — [Kafka table engine](https://clickhouse.com/docs/integrations/kafka/kafka-table-engine), ClickPipes GA, all SDKs |
| **Pulsar** | Broker producer deduplication: named producer + sequence id; client MUST "retry infinitely" with message timeout 0 to keep ordering ([dedup cookbook](https://pulsar.apache.org/docs/5.0.x/cookbooks-deduplication/)) | "Per-key-partition: all messages with the same key will be in order and be placed in same partition" ([concepts-messaging](https://pulsar.apache.org/docs/5.0.x/concepts-messaging/)) | Retention size/time per namespace; `-1/-1` = infinite ([retention cookbook](https://pulsar.apache.org/docs/cookbooks-retention-expiry/)) | Low-medium: custom consumer; built-in tenant/namespace (fits 7k tenants) |
| **NATS JetStream** | At-least-once ack loop; unacked messages redeliver after Ack Wait (30 s default); **MaxAckPending** caps in-flight (1,000 shown) ([delivery & ack](https://docs.nats.io/learn/jetstream/delivery-and-acknowledgment)) | Stream order holds, but **redelivery arrives out of stream order**; strict order needs MaxAckPending=1 at throughput cost ([delivery & ack](https://docs.nats.io/learn/jetstream/delivery-and-acknowledgment)) | Replay from any sequence (`DeliverPolicy: All`); server dedup via `Nats-Msg-Id` with **2-minute default window** ([publishing](https://docs.nats.io/learn/jetstream/publishing)) | Medium: custom consumer; dedup must not rely on the 2-min window |
| **Kinesis** | At-least-once via KCL; sequence numbers assigned by the service | Sequence number "unique per partition-key within its shard"; partition key MD5→shard ([key concepts](https://docs.aws.amazon.com/streams/latest/dev/key-concepts.html)) | Retention 24 h default, up to 8,760 h (365 days) ([key concepts](https://docs.aws.amazon.com/streams/latest/dev/key-concepts.html)) | Medium-high: shard planning; ≤1 MB/s and 1,000 rec/s per shard |
| **SQS** | Standard queues: **at-least-once, duplicates possible, "messages may occasionally arrive out of order"** ([standard queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues.html)) | Ordering only in FIFO queues via message groups (Developer Guide, FIFO queues) | **None** — acked messages deleted; replay impossible | High for ledger duty; front door only |
| **Azure Service Bus** | Peek-lock → at-least-once; **duplicate detection** on `MessageId`, 10-min default window (20 s–7 days), window size taxes throughput ([dup detection](https://learn.microsoft.com/en-us/azure/service-bus-messaging/duplicate-detection)) | FIFO only inside **sessions** — one exclusive receiver lock per `SessionId`; parallel consumers demultiplex cleanly ([sessions](https://learn.microsoft.com/en-us/azure/service-bus-messaging/message-sessions)) | None; session state (256 KB Standard/100 MB Premium) is not replay | Medium: sessions + `partitionkey`=user_id |
| **RabbitMQ** | Acknowledgements → "**at least once**"; confirms imply publisher-side retries, so consumers must be idempotent; `redelivered` flag hints repeats ([reliability guide](https://www.rabbitmq.com/docs/reliability)) | Ordered per queue | Acked messages gone — no history replay ([reliability guide](https://www.rabbitmq.com/docs/reliability)) | Medium: quorum-queue adapter + DLX for rejects |

**Verdict:** Kafka/Pulsar are ledger-grade; JetStream works if the ledger, not the server, owns dedup; SQS/ASB/RabbitMQ stay valid adapters but are never trustworthy for historical replay. The contract lives in the envelope + ClickHouse idempotency.

## 3. ClickHouse ingestion best practices (current docs)

**Batching.** Synchronous inserts: batch ≥1,000 rows, ideally 10k–100k, and keep ~1 insert query/s per table so background merging keeps up (`max_insert_block_size` ≈1M rows/part); prefer Native+LZ4 or RowBinary; JSONEachRow is "expensive to parse" ([insert strategy](https://clickhouse.com/docs/concepts/best-practices/selecting-an-insert-strategy)).

**async_insert.** Flush triggers: `async_insert_max_data_size` 100 MiB, adaptive busy timeout 50–200 ms OSS (1,000 ms Cloud) since 24.2, `async_insert_max_query_number` 450; buffers are per query-shape and per node ([async inserts](https://clickhouse.com/docs/optimize/asynchronous-inserts)). Gotchas: schema/validation errors reject **the entire query's payload** at flush; `wait_for_async_insert=0` (fire-and-forget) has "no dead-letter queue for failed inserts" and kills server-side backpressure — keep `=1` ([async inserts](https://clickhouse.com/docs/optimize/asynchronous-inserts)). High-cardinality partition keys still risk too-many-parts.

**Kafka table engine.** At-least-once; duplicates possible when insert succeeds but offset commit fails, and block dedup "relies on identical blocks… a Kafka rebalancing may invalidate this assumption" ([Kafka engine](https://clickhouse.com/docs/integrations/kafka/kafka-table-engine)). "100k rows/sec on a single table engine should be considered obtainable"; `kafka_max_block_size` defaults to 1,048,576; total consumers ≤ topic partitions; `kafka_num_consumers`+`kafka_thread_per_consumer=1` parallelize; `kafka_skip_broken_messages` is not a production DLQ ([Kafka engine](https://clickhouse.com/docs/integrations/kafka/kafka-table-engine)).

**Dedup mechanics.** Every MergeTree insert gets a `block_id` (hash of data); duplicates are dropped when a dedup log exists. `*ReplicatedMergeTree` keeps one by default; plain `MergeTree` needs `non_replicated_deduplication_window>0` (default 0). Query-level: `deduplicate_insert` (default `enable` since 26.2 for sync + async) and `insert_deduplication_token` to identify inserts by caller-chosen string. MV destinations dedup only with `deduplicate_blocks_in_dependent_materialized_views=1`, and each view must emit "one block in, one block out" — fan-out joins break dedup; inserts that overflow the dedup log window lose dedup ([dedup on retries](https://clickhouse.com/docs/concepts/features/operations/insert/deduplicating-inserts-on-retries)).

**Eventual layer.** `ReplacingMergeTree(ver)` collapses same-`ORDER BY`-key rows only during merges — "does not guarantee the absence of duplicates"; correct reads require `FINAL` with max-`ver` winning. Backstop, not primary dedup ([ReplacingMergeTree](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/replacingmergetree)).

**Schema registry.** Native `AvroConfluent` format: magic byte `0x00` + 4-byte schema id, resolved via `format_avro_schema_registry_url`; typed map (`long (timestamp-millis)`→`DateTime64(3)`, unions→`Nullable`/`Variant`) ([AvroConfluent](https://clickhouse.com/docs/reference/formats/Avro/AvroConfluent)). JSON Schema has no native engine path — either adopt a Confluent-compatible Avro registry, or keep JSON wire + validate before insert.

## 4. Idempotent consumer, DLQ, backpressure, replay

- **Idempotency (layered):** (1) ClickHouse block dedup on identical retry batches; (2) `insert_deduplication_token` = deterministic digest of the ingested batch range; (3) `event_id = hash(source,id)` + `ReplacingMergeTree(event_time)`/`FINAL` in projector reads ([dedup on retries](https://clickhouse.com/docs/concepts/features/operations/insert/deduplicating-inserts-on-retries)). Broker dedups (Pulsar named producer, NATS 2-min, ASB ≤7 days) are opportunistic only.
- **DLQ:** follow the ClickPipes pattern — malformed records land in `<dest>_clickpipes_error` (7-day TTL) while ingestion continues; pipes retry operational failures automatically ([ClickPipes](https://clickhouse.com/docs/integrations/clickpipes/home)). Adapter equivalents: Kafka/SQS/ASB native DLQs, NATS `term` ack (+ `MaxDeliver`), ASB `MaxDeliveryCount` default 10 ([sessions](https://learn.microsoft.com/en-us/azure/service-bus-messaging/message-sessions)), RabbitMQ DLX. A poison signal must never stall a user's ordered stream.
- **Backpressure:** consumer withholds acks → broker redelivers/caps (JetStream MaxAckPending; Kafka lag + `max.poll.interval`); with `wait_for_async_insert=1` the insert call itself blocks until flush, giving consumer→ClickHouse pressure; fire-and-forget modes are explicitly unsafe ([async inserts](https://clickhouse.com/docs/optimize/asynchronous-inserts)).
- **Replay:** ledger = truth; projector rebuild re-runs the deterministic spec from the ledger. Broker retention (Kafka offset reset within retention; Pulsar `-1/-1` optional infinite; NATS any sequence; Kinesis ≤365 days) is an operational cushion, not the system of record ([Pulsar retention](https://pulsar.apache.org/docs/cookbooks-retention-expiry/), [Kinesis](https://docs.aws.amazon.com/streams/latest/dev/key-concepts.html)).

## 5. Rough throughput math

Anchors, then arithmetic. One Kafka table engine ≈100k rows/s obtainable, scaling with `kafka_num_consumers` up to the partition count ([Kafka engine](https://clickhouse.com/docs/integrations/kafka/kafka-table-engine)). Synchronous ceiling ≈1 insert/s × 10k–100k rows = 10k–100k rows/s per table — the reason a batching consumer exists; async inserts hold part creation ≈1/s regardless of client count (200→500 clients benchmarked with stable parts and CPU) ([async-inserts blog](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse)). Fleet headroom dwarfs our stage: ClickHouse is "intended to receive millions of row inserts per second"; Cloudflare stores 11M rows/s; Uber millions of log lines/s ([async-inserts blog](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse)). **Planning line:** a 2–4 vCPU node on a 10-partition, ~1 KB-event feed with a batching consumer (10k-row blocks, ~1 part/s, `wait_for_async_insert=1`) safely carries ~50k events/s with merge headroom; horizontal partition/node scaling covers 7,000 tenants and keeps node budget for the read path.

## Recommended envelope + consuming design for the spec

1. **Envelope:** CloudEvents 1.0.2 (structured JSON for HTTP + adapter normalize; binary mode optional on Kafka). Extra REQUIRED extension attribute `partitionkey=user_id`; `dataschema` versioned registry URI.
2. **Ordering rule (hard):** all events for one `user_id` carry identical `partitionkey`; adapters map it to native order primitives — Kafka key/partition, Pulsar per-key partition, SQS FIFO message group, ASB `SessionId`, NATS consumer+`Nats-Msg-Id`. Projector assumes per-user arrival order, no cross-user order.
3. **Delivery posture:** design to at-least-once; identical `source`+`id` duplicates are dropped by ClickHouse block/row dedup; "exactly-once" claims are rejected at spec level.
4. **Ingest write path:** batching consumer per broker → ledger: ≥1,000-row blocks (target 10k–100k), Native+LZ4 or JSONEachRow over HTTP, ~1 part/s per table-partition, `wait_for_async_insert=1`, no distributed-table indirection on the hot path.
5. **Accuracy:** projector reads via `FINAL` over `ReplacingMergeTree(event_time)` with `event_id` uniqueness; the ledger stays append-only and unchanged content.

## So what for the spec

- **Adopt CloudEvents 1.0.2 + `partitionkey` extension as the signal envelope** — dedup contract (`source`+`id`), schema pointer (`dataschema`), and ordering key all exist; skip a custom envelope.
- **Per-user ordering is mandatory**, with the broker mapping above: per-user in-order, cross-user unordered.
- **Ingestion is at-least-once by design**: ClickHouse-side dedup (`insert_deduplication_token`, ReplacingMergeTree/FINAL) is the correctness owner; broker features are accelerators.
- **Non-replicated `MergeTree` dedup defaults OFF** — set `non_replicated_deduplication_window` or use replicated tables.
- **Bound broker dedup reliability:** NATS 2-min window, ASB 10-min (max 7-day) window, Pulsar names-producer — treat all as best-effort; ledger dedup is authoritative.
- **DLQ per ingest route with bounded redelivery** (ClickPipes-style error table, NATS `term`/`MaxDeliver`, ASB `MaxDeliveryCount=10` default, RabbitMQ DLX); poison events never block a user's stream.
- **Backpressure chain specified:** no-ack → broker cap/redelivery; `wait_for_async_insert=1` blocks consumer; fire-and-forget forbidden.
- **Broker roles pinned:** Kafka/Pulsar ledger-grade; JetStream acceptable; SQS/ASB/RabbitMQ buffered front doors only — no historical replay from them.
- **Schema registry alignment:** AvroConfluent-compatible registry for normalized consumers; JSON wire format; `dataschema` URIs versioned additive-only.
- **Capacity:** plan ~50k events/s per modest batching-consumer node (documented pars: 100k rows/s per engine; 11M rows/s fleet-level), scale horizontally, keep ingest batch cadence independent of the <2 s read SLA.
