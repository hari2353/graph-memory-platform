# Research 05 — Output channels, observability/evaluation, and cost engineering (2026-10-20)

## TL;DR

- REST, webhooks, and SDKs are **thin adapters over one "channel core"**; MCP stays primary. The core owns idempotency, cursor pagination, cache metadata, rate-limit headers; channels differ only in transport.
- Stripe is the REST reference: `Idempotency-Key` (≤255 chars, retried responses replayed, ~24 h) ([Stripe](https://docs.stripe.com/api/idempotent_requests.md)); cursor pagination `limit=1–100`, `has_more` ([Stripe](https://docs.stripe.com/api/pagination.md)); 100 rps live global / 25 per endpoint, 429 + retry etiquette ([Stripe](https://docs.stripe.com/rate-limits.md)).
- Webhooks: HMAC-SHA256 over `{timestamp}.{raw body}`; verify the raw body; reordering/duplicates are normal — dedupe on event IDs ([Stripe](https://docs.stripe.com/webhooks); [Svix/Standard Webhooks](https://docs.svix.com/receiving/verifying-payloads/how.md)). Retries ~3 days exponential (Stripe) / Svix ladder ([Svix](https://docs.svix.com/retries)); **order is best-effort — strict FIFO is opt-in and throttles throughput** ([Svix](https://docs.svix.com/advanced-destinations/fifo-endpoints)).
- Langfuse ingests OTLP/HTTP at `<region>/api/public/otel` with `Authorization=Basic <base64(pk-lf-…:sk-lf-…)>` (percent-encoded `Authorization=Basic%20…` in env vars) and `x-langfuse-ingestion-version: 4`; gRPC unsupported ([Langfuse](https://langfuse.com/integrations/native/opentelemetry)).
- OTel GenAI semantic conventions **moved to a dedicated repo** ([OTel](https://opentelemetry.io/docs/specs/semconv/gen-ai/), [repo](https://github.com/open-telemetry/semantic-conventions-genai)) and are "still evolving" — Langfuse's `langfuse.*` mapping is the stable contract ([Langfuse](https://langfuse.com/integrations/native/opentelemetry)).
- At 350M events/day, sample: head sampling at **1% or lower** stays representative for high-volume systems; tail-sample errors/slow traces in a Collector ([OTel](https://opentelemetry.io/docs/concepts/sampling/)).
- Langfuse experiments (datasets → runs → scores) ingest via plain OTel attributes — memory-quality evals run directly on our ClickGraph spans ([experiments via OTEL](https://langfuse.com/docs/evaluation/experiments/experiments-via-opentelemetry.md), [data model](https://langfuse.com/docs/evaluation/experiments/data-model.md)).
- Personalization value: offline hit-rate@k + counterfactual replay, online lift with ≥1-week windows ([LaunchDarkly](https://launchdarkly.com/docs/home/experimentation/size)); Eppo requires minimum duration **and** sample size per variant ([Eppo](https://docs.geteppo.com/experiment-analysis/configuration/analysis-plans/)).
- Cost: 350M events/day × 1 KB raw compresses ~10× to ~1.1 TB/mo ([CH pricing](https://clickhouse.com/pricing)); async inserts mandatory for raw small writes ([CH](https://clickhouse.com/docs/concepts/features/operations/insert/asyncinserts.md)); steady state: self-hosted ≈ $790/mo vs ClickHouse Cloud ≈ $3,150–3,750/mo.

## 1. Output channels (REST / webhooks / SDKs) as channel adapters

One core with a `ChannelAdapter` seam. Channels differ in transport only; the core owns resource naming, envelope versioning, degradation horizon, scoring weights, and cache control.

**REST (pull, cacheable).** Versioned user-scoped reads: `GET /v1/{tenant}/users/{user_id}/context?tools=…` returning the same payload MCP returns. From Stripe: `Idempotency-Key` on state-changing writes (≤255 chars, first response replayed on retry, keys pruned ~24 h) ([Stripe](https://docs.stripe.com/api/idempotent_requests.md)); cursor pagination (`limit` 1–100, `starting_after`/`ending_before`, `has_more`) with SDK auto-pagination helpers ([Stripe](https://docs.stripe.com/api/pagination.md)); 429 + reason header, retries with **backoff + jitter / token bucket** ([Stripe](https://docs.stripe.com/rate-limits.md)) — mirror as `X-RateLimit-*`/`Retry-After`. `ETag`/`If-None-Match` revalidation ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/ETag)) using the context digest (projection version + weight hash) as validator; per-request version pinning → `Context-Version` header.

**Webhooks (push, at-least-once).** Outbound for `recommendation.created`, `outcome.recorded`, `effectiveness.changed`. Standard Webhooks/Svix scheme: `webhook-id`/`webhook-timestamp`/`webhook-signature` headers (Svix aliases `svix-*`), HMAC-SHA256 over `{id}.{timestamp}.{raw body}`, `whsec_` secret, constant-time compare, ~5-minute timestamp tolerance against replays ([Svix](https://docs.svix.com/receiving/verifying-payloads/how.md)); Stripe's equivalent is `{t}.{payload}` in `Stripe-Signature`, v1-only schemes, same raw-body rule ([Stripe](https://docs.stripe.com/webhooks)). Delivery contract: retries (Stripe: 3 days exponential; Svix ladder immediately → 10 h), success = fast 2xx (3xx = failure), failing endpoints disabled after ~5 days with an operational webhook, **ordering not guaranteed and duplicates happen — consumers dedupe on event IDs, never timestamps** ([Stripe](https://docs.stripe.com/webhooks); [Svix](https://docs.svix.com/retries)). Strict ordering costs throughput (FIFO blocks until prior ack) ([Svix FIFO](https://docs.svix.com/advanced-destinations/fifo-endpoints)) — per-endpoint option, default best-effort, plus a monotonic sequence + `previous_event_id` for gap detection.

**SDKs (thin only).** Thin typed clients over REST (auth, pagination auto-fetch, retries), no business logic — Stripe SDKs are exactly such wrappers ([Stripe](https://docs.stripe.com/api/pagination.md)); Svix likewise recommends thin wrappers over its verify primitives ([Svix](https://docs.svix.com/consuming-webhooks)). Warrant one only for (a) non-trivial per-language auth or (b) default-on telemetry (SDK prewires our OTel export); otherwise curl-able REST suffices.

## 2. OpenTelemetry → Langfuse + trace strategy

- **Endpoint/auth**: OTLP/HTTP (JSON + protobuf; gRPC unsupported) at `https://cloud.langfuse.com/api/public/otel` (EU; US/JP/HIPAA) or `http://localhost:3000/api/public/otel` self-host ≥ v3.22.0. Auth via `OTEL_EXPORTER_OTLP_HEADERS="Authorization=Basic ${AUTH_STRING},x-langfuse-ingestion-version=4"`, `AUTH_STRING = base64(pk-lf-…:sk-lf-…)`; env-form headers typically need `Authorization=Basic%20…` — ClickGraph's `CLICKGRAPH_OTLP_HEADERS` matches. Without the v4 header, ingested OTel data "can be delayed by up to 10 minutes"; signal-specific exporters use `/api/public/otel/v1/traces` ([Langfuse](https://langfuse.com/integrations/native/opentelemetry)).
- **Semantic conventions**: GenAI semconv moved to the dedicated [open-telemetry/semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai) repo (spans/metrics/events for GenAI clients, **MCP included**) ([OTel](https://opentelemetry.io/docs/specs/semconv/gen-ai/)); adopt `gen_ai.*` but treat Langfuse's `langfuse.*` mappings (`langfuse.user.id`, `langfuse.session.id`, `langfuse.trace.tags`, `langfuse.observation.type`; precedence over gen-ai, baggage propagation to every span, unrecognized types fall back to `span`) as the working contract ([Langfuse](https://langfuse.com/integrations/native/opentelemetry)).
- **Sampling for ~350M-events/day telemetry**: head sampling decides early per trace (cheap, whole traces kept); tail sampling keeps errors/high-latency after seeing the trace but needs a stateful Collector ([OTel](https://opentelemetry.io/docs/concepts/sampling/)). Plan: head 100% in dev; in prod, a Collector with tail policies (always errors, p99 latency, first-session-per-user) + 1–5% probabilistic otherwise, batch + `memory_limiter` before export ([Langfuse collector yaml](https://langfuse.com/integrations/native/opentelemetry)). Keep an unsampled ClickHouse span-stub table for per-tenant auditability; only sampled spans reach Langfuse.
- **Evaluation surfaces**: datasets/items/runs bind traces to expected outputs and scores, and experiment metadata rides on plain OTel spans ([experiments via OTEL](https://langfuse.com/docs/evaluation/experiments/experiments-via-opentelemetry.md), [data model](https://langfuse.com/docs/evaluation/experiments/data-model.md)) — memory-graph snapshots become dataset items without a second eval system.

## 3. Proving personalization value (evaluation design)

**Offline.** (1) *Context hit-rate@k*: replay sampled real agent requests; k = 5 context items; hit = item cited in the agent's final answer (LLM-as-judge in Langfuse, human spot-audit), per tenant and signal type; the `outcomes` ledger is ground truth. (2) *Counterfactual replay*: the deterministic projection makes this cheap — rebuild the user's graph at T-δ, re-serve the historical request, compare against what actually happened (recommendation→outcome link gives a within-user rank metric). (3) *Held-out lift*: task-success windows with memory alive vs a kill-switch on the same users — the cheapest honest lift signal.

**Online A/B conventions.** Randomize per user (not tenant), sticky. Guardrails first: p95 latency < 2 s (SLA), 401/429 rates, reflection lag, token cost/session. Windows: LaunchDarkly recommends ≥ **one full week**, longer for seasonality ([LaunchDarkly](https://launchdarkly.com/docs/home/experimentation/size)); Eppo plans enforce **minimum duration and sample size/variant** ([Eppo](https://docs.geteppo.com/experiment-analysis/configuration/analysis-plans/)) with MDE-based duration estimation ([Eppo MDE](https://docs.geteppo.com/statistics/sample-size-calculator/mde/)); Statsig warns against naive-peeking early stops ([Statsig](https://www.statsig.com/blog/making-early-decisions-on-experiments)). Our rule: pre-registered plan (primary metric `agent_task_success@14d`), fixed 2-week runs, no auto-stop; the recommendations→outcomes→effectiveness loop derives its weights from this same telemetry.

## 4. ClickHouse cost engineering at 7,000 tenants

**Levers (documented).**

| Lever | What ClickHouse docs specify |
|---|---|
| TTL / rollup | Row/column TTL (`TTL ts + INTERVAL … DELETE`); rollup via `TTL … GROUP BY … SET` keeps aggregates while dropping detail; applies during merges (`merge_with_ttl_timeout` default 14,400 s); partition by day/month matching the TTL field so expiry drops partitions ([CH TTL](https://clickhouse.com/docs/concepts/features/operations/delete/ttl.md)) |
| Hot/warm/cold | `TTL ts TO VOLUME 'hot_volume'` … `TO VOLUME 'cold_volume'` over disk/volume config; Cloud does not offer this tiering; S3-backed disks give compute-storage split on self-managed ([CH TTL](https://clickhouse.com/docs/concepts/features/operations/delete/ttl.md), [sizing](https://clickhouse.com/docs/guides/oss/best-practices/sizing-and-hardware-recommendations.md)) |
| Codecs | Fix data types + `ORDER BY` first — right types + ordering halved the stack-overflow demo table's compressed size (50.16 → 25.15 GiB) in the docs example; then `ZSTD` (Cloud default ZSTD(1)), `Delta, ZSTD` on monotonic IDs/timestamps, `LZ4` only where compression ties since it decompresses cheapest ([CH compression](https://clickhouse.com/docs/guides/clickhouse/data-modelling/compression/compression-in-clickhouse.md)) |
| async_insert | Server-side buffering (100 MiB / ~200–1,000 ms / 450 queries thresholds), durable with `wait_for_async_insert=1` (recommended; `0` risks silent loss); validation at flush; adaptive since 24.2; auto-dedup of retried inserts since 26.2 — per-event HTTP inserts at 350M ev/day **must** use this ([CH async_insert](https://clickhouse.com/docs/concepts/features/operations/insert/asyncinserts.md)) |
| Projections vs MVs | Projections: per-table, optimizer-selected, auto-maintained — but no JOIN/WHERE filters, no `FINAL`, no parallel replicas; MVs: explicit tables, chainable, pre-joining/denormalization, but fire only on INSERT and ignore UPDATE/DELETE — our ledger/projection tables are append-only, so both survive; pick MVs when the graph needs multi-stage pipelines, projections for alternate sort orders on one table ([CH MVs vs projections](https://clickhouse.com/docs/concepts/features/projections/materialized-views-versus-projections.md)) |

**Cost model.** 7,000 tenants × 50,000 events/tenant/day = **350M events/day** = 10.7 B events/month. Assumption: 1.0 KB raw/event → 350 GB/day raw; ClickHouse's own 10× ("÷10 uncompressed") conversion ([CH pricing](https://clickhouse.com/pricing)).

| Step | Arithmetic | Result |
|---|---|---|
| Ingest | 350M ev/d × 1.0 KB | 350 GB/d raw ≈ 10.7 GB/min |
| On-disk | 350 GB/d ÷ 10 | 35 GB/d ≈ 1.07 TB/mo compressed |
| Steady state (12-mo ledger) | 1.07 TB × 12 | **≈ 12.8 TB** by month 12 |
| Hot (90 d) on NVMe | 1.07 TB/mo × 0.25 | ≈ 3.2 TB hot, 9.6 TB cold on S3 |
| S3 cold | 9,830 GB × $0.023/GB-mo ([AWS S3](https://aws.amazon.com/s3/pricing/)) | ≈ $226/mo |
| Self-hosted compute+hot NVMe | 3 nodes (16 vCPU, 64 GB, 2 TB NVMe) ≈ $2,500 capex each → 36-mo amortization $208/mo + $350 power/colo/bandwidth; per CH guidance 1:30–1:50 RAM:hot-storage → 65–107 GB RAM for 3.2 TB hot ([sizing](https://clickhouse.com/docs/guides/oss/best-practices/sizing-and-hardware-recommendations.md)) | ≈ $560 + $226 S3 ≈ **$790/mo** ClickHouse layer |
| CH Cloud compute | 2 replicas × 48 GiB RAM = 12 CU × $0.39030/unit-hr (us-east-1 Enterprise) × 732 h ([CH pricing](https://clickhouse.com/pricing)) | $3,428/mo |
| CH Cloud storage | 12.8 TB × $25.30/TB-mo us-east-1 | $324/mo |
| Cloud total (month-12 run rate) | $3,428 + $324 | **≈ $3,750/mo** (GCP us-central1: 12 CU × $0.32727 × 732 = $2,875 + 12.8 × $22.00 = $282 ≈ **$3,150/mo**) |

Self-hosted ≈ $0.8k/mo vs Cloud ≈ $3.2–3.8k/mo at month-12 steady state; Cloud adds ~$22–25/TB/mo frictionlessly, self-hosted needs planned NVMe expansion or earlier tier-to-S3. Shorter retention cuts both: 30-day hot + 6-month ledger TTL with `GROUP BY … SET` rollups keeping effectiveness aggregates ≈ 3.2 TB total → Cloud ≈ $1.6–1.9k/mo, self-hosted ≈ $700/mo ([CH TTL](https://clickhouse.com/docs/concepts/features/operations/delete/ttl.md)). CH's sizing doc cites a telecom 38-node/1,600-vCPU 30-day ledger — an order of magnitude above ours ([sizing](https://clickhouse.com/docs/guides/oss/best-practices/sizing-and-hardware-recommendations.md)).

## So what for the spec

- **Channel adapter is a first-class SRP seam**: `ContextService` (pure) behind `McpAdapter | RestAdapter | WebhookAdapter | SdkPublisher`; all adapters call the same versioned payload builder, so REST output == MCP output at a given projection revision.
- REST v1 must spec user-scoped reads, `Idempotency-Key` on writes ([Stripe](https://docs.stripe.com/api/idempotent_requests.md)), cursor pagination with `has_more` ([Stripe](https://docs.stripe.com/api/pagination.md)), `ETag`/`If-None-Match` + `Context-Version` ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/ETag)), 429 + `Retry-After` ([Stripe](https://docs.stripe.com/rate-limits.md)).
- Webhooks: HMAC-SHA256 `{id}.{ts}.{raw body}` per Standard Webhooks ([Svix](https://docs.svix.com/receiving/verifying-payloads/how.md)); fast-2xx contract; Stripe/Svix-style retry ladder with endpoint-disable notification ([Stripe](https://docs.stripe.com/webhooks), [Svix](https://docs.svix.com/retries)); per-endpoint ordering option (default best-effort) + payload sequence for gap detection; consumers dedupe by event ID.
- SDKs are thin REST wrappers prewired with OTel — no business logic in SDK code ([Stripe](https://docs.stripe.com/api/pagination.md)).
- Langfuse wiring locked: `/api/public/otel`, Basic auth (percent-encoded `Authorization=Basic%20…`), `x-langfuse-ingestion-version: 4`, OTLP/HTTP only ([Langfuse](https://langfuse.com/integrations/native/opentelemetry)); ClickGraph's existing OTLP header config validated by an acceptance test.
- Sampling policy is config, not code: per-tenant head rate + tail rules (errors, p99); unsampled CH span-stub table preserves full auditability while only sampled spans reach Langfuse ([OTel](https://opentelemetry.io/docs/concepts/sampling/)).
- Every experiment ships with a pre-registered plan: primary metric, guardrails, ≥1-week window / sample-size or sequential-test rules ([LaunchDarkly](https://launchdarkly.com/docs/home/experimentation/size), [Eppo](https://docs.geteppo.com/experiment-analysis/configuration/analysis-plans/)); Langfuse datasets carry context snapshots + outcome-derived expected outputs ([Langfuse](https://langfuse.com/docs/evaluation/experiments/data-model.md)).
- Cost levers live in the schema: daily partitions aligned with TTL, `TTL … GROUP BY … SET` rollups, `Delta,ZSTD` on ids/timestamps, `LowCardinality` enums ([CH TTL](https://clickhouse.com/docs/concepts/features/operations/delete/ttl.md), [compression](https://clickhouse.com/docs/guides/clickhouse/data-modelling/compression/compression-in-clickhouse.md)); `async_insert=1,wait_for_async_insert=1` wherever ingest isn't client-batched ([CH async_insert](https://clickhouse.com/docs/concepts/features/operations/insert/asyncinserts.md)).
- Cost story in one line: 1.07 TB compressed/mo → 12.8 TB at 12-month retention; default self-hosted (3 nodes ≈ $790/mo incl. S3 cold) with ClickHouse Cloud (≈ $3.15–3.75k/mo) as the benchmarked alternative; re-check the 90-day hot split against measured SLAs.
